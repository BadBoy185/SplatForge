# M9 reconstruction validation and selection

M9a and M9b are implemented. [M10](M10.md) consumes their immutable outputs. Technical acceptance and
representative empirical recommendation benchmarks are separate gates.

M9a observes immutable reconstruction data. It never changes M8, launches a mapper,
filters points, performs bundle adjustment or merges/aligns components. M10 dataset
preparation is outside this milestone. M7c representative VPR and M8 representative
mapper recommendation benchmarks remain independently pending.

## Measurement contracts

`ValidationUniverse` v1 records the exact selected view UUID, source UUID, source-group
UUID, camera-group UUID and media type. The classical reader follows validated immutable
lineage: ReconstructionSet -> VerifiedGeometrySet -> MatchSet -> LocalFeatureSet ->
SelectedViewSet/CandidateViewSet. It accepts fixed-FPS and sharpest historical selections.
The UUID set must equal ReconstructionSet.input_view_ids; mismatch refuses the input.
Current project labels, source intent and filenames cannot supply this universe.

`ValidationGeometryInput` v1 is M9-owned. Its canonical per-component content digest includes
M8 camera/pose semantics and a sorted stream of point digests. A parallel reference digest
freezes consumed original camera intrinsics/sharing; measurements depend on both, while
downstream selected-content identity excludes reference-only changes. Each point digest
covers float64 XYZ and canonical observations
(public view UUID, keypoint index, observed pixel XY). Sorted observation membership
defines tracks. Signed zero is normalized. Native point/image/camera IDs, folder numbers,
binary record layout, color, stored native errors, paths and timestamps are excluded.
ReconstructionSet v1 and its semantic digest remain unchanged.

`ReconstructionMetrics` v1 separates expensive measurements from thresholds. Numerical
identity depends on ReconstructionSet semantics, detailed validation geometry, exact
universe and MeasurementSettings v1. It excludes thresholds, mapper label, selection,
M10, runtime, artifact UUID and wording. The geometry transport scan has its own normal
artifact/cache recipe over verified native payload hashes. Repacking a model can rerun
canonicalization while producing the same geometry/measurement identity. Threshold-only
changes reuse geometry and measurements; ordinary upstream integrity checks still run.

## Availability and algorithms

Every measurement carries `exact`, `sampled` or `unavailable`. Unavailable evidence has a
bounded reason and null value, never zero/NaN/a fabricated empty distribution. A zero
point count is exact; the distribution of an empty population is unavailable.

Coverage is exact: registered selected UUIDs / input selected UUIDs, overall, per component,
source and source group. Counts and ratios are stored together. Source-group denominator
always includes that group's unregistered selected views. Fragmentation stores descending
component sizes, largest/second-largest coverage and registered fraction outside largest.
These facts do not declare intentional disconnected scenes incorrect.

Camera diagnostics are model-aware: min/max focal / max(image dimensions), maximum
principal-point offset `max(abs(cx/width-.5), abs(cy/height-.5))`, maximum absolute extra
distortion parameter, maximum absolute relative focal change from frozen input, camera
model counts and sharing-partition mismatch count. Unknown model interpretation is
unavailable. Missing frozen focal references are unavailable. No physical calibration
truth is inferred from a nominal input focal length.
Sharing compares the actual frozen mapper-prior partition, not candidate groups where
cameras merely may share calibration. Arbitrary prior-group labels do not enter geometry identity.

Current COLMAP direct projection supports SIMPLE_PINHOLE, PINHOLE, SIMPLE_RADIAL,
RADIAL, OPENCV and FULL_OPENCV, including their declared radial/tangential/rational
distortion. Reprojection is computed from final camera/pose, XYZ and actual pixel XY.
Equations and parameter order were checked against the pinned
[COLMAP camera definitions](https://github.com/colmap/colmap/blob/bd1fcf6/src/colmap/sensor/models.h).
Count, mean, RMS, min/max are exact streaming aggregates over supported observations.
Median/p90/p95/p99 use nearest-rank exact quantiles up to quantile_sample_bound=10000;
beyond it SHA-256 bottom-k sampling uses point content plus public observation identity.
Sample method/count/population are recorded. Native order/IDs and random seeds do not
select samples. Partial projection support makes whole-component errors unavailable;
supported-subset statistics and undefined/supported counts remain explicit.

Point/observation counts and observations per registered view are exact. Integer track
histograms give exact min/max/mean/median/p90, two-view counts/fractions and long-track
counts/fractions. Long means >=10 observations by default, explicitly configurable.
No complete point cloud/error array is accumulated in Python memory.

Triangulation uses maximum acute ray angle (degrees) per point. Up to 16 rays per track
are chosen by public view UUID hash; at most 120 pairs are evaluated per point. Longer
tracks explicitly mark the resulting angle statistics and low-angle fraction sampled,
with selected/population pair counts. Angle quantiles additionally use bounded bottom-k
sampling when needed. Low angle means <1 degree by default. Zero/insufficient rays are
missing evidence. Numerical sampling settings are frozen and affect measurement recipes.
Triangulation distributions use defined ray angles; exact measured/unmeasurable point
counts make insufficient support explicit. Combined ray/quantile sampling retains both
methods and their sample/population evidence.
Refusal-only native byte/scratch/timeout limits do not; failure never reduces sample size.

The adapter normalizes native observations immediately and uses an owned disk-backed
SQLite scratch index for canonical streaming. It leaves native payloads read-only.
Future cameras-only/points-only/direct representations implement the small validation
source protocol and declare detailed capabilities; sparse tracks are not mandatory.

## Baseline policy

`ReconstructionValidationPolicy` v1 has one initial `baseline_v1` profile. Changed fields
require `policy_id=custom_v1`; resolved settings are saved. Warnings are heuristics awaiting
representative benchmark calibration, not universal physical truth.

| Warning condition | Default |
| --- | --- |
| Overall registration below | 0.70 |
| Largest component/input coverage below | 0.60 |
| Project/component source-group coverage below | 0.25 |
| Registered fraction outside largest above | 0.25 |
| Focal/image ratio outside | 0.1 .. 10 |
| Principal-point normalized offset above | 0.5 |
| Absolute distortion/extra parameter above | 1.0 |
| Relative final/input focal change above | 0.5 |
| Camera sharing partition mismatches above | 0 |
| Reprojection p95 above | 4 pixels |
| Triangulation median below | 1 degree |
| Two-view track fraction above | 0.8 |

The baseline component hard gate is >=3 registered cameras. Existing M8 structural
corruption/no-component/input mismatch is refused before publishing a quality report.
Optional custom hard thresholds cover overall coverage, component coverage, source-group
coverage, reprojection p95 and triangulation median. None is enabled implicitly.
All detailed metrics are optional in baseline. Unknown values remain in typed unknown
summaries. Explicit required metrics choose warning/failure when unavailable and whether
sampled evidence suffices. A PASS policy status means no configured issue fired; it does
not convert missing numerical evidence into a passing measurement.

`ReconstructionValidationReport` v1 references exact metrics/reconstruction artifacts via
normal manifest lineage. It retains overall/project/component status, structured issues
and unknown summaries, without duplicating large measurements. Issue severity is warning
or failure; PASS means no issue. Scope is project, component or source group (with explicit
optional component identity). Stable issue IDs hash report semantic identity + issue code
+ scope. Wording alone changes neither numerical report digest nor issue IDs.

## Execution and CLI

The three explicit one-node routes `reconstruction.geometry`, `reconstruction.measure`
and `reconstruction.validate` use existing run snapshots, attempts, writer lease,
publication, cache, cancellation and orphan recovery. They publish small `evidence.json`
receipts under normal artifact storage. No project/state/M8 format migration is needed.
The validate command returns all three run references; validation-show uses the report run.

```powershell
splatforge reconstruction validate "C:\Scenes\Example" --mapping-run <uuid> --json
splatforge reconstruction validate "C:\Scenes\Example" --mapping-run <uuid> --policy custom.json
splatforge reconstruction validation-show "C:\Scenes\Example" <validation-run-id> --json
```

`--measurement-settings` accepts typed JSON. Resource defaults are 32 GiB native bytes,
128 GiB scratch, 7200 seconds, configurable with --max-native-gib/--max-scratch-gib/--timeout.
Metadata preflight defaults to 1000 components and 250000 source/component coverage cells,
configurable with --max-components/--max-coverage-cells. Cells are exactly
`component_count * (source_count + source_group_count)`. Refusal happens before detailed
scanning/allocation. Component metadata is bounded incrementally and every evidence JSON
has a 64 MiB structural limit checked before writing. These are resource/representation
limits, not quality gates; raising inactive limits changes no numerical identity. No
component is dropped and no sampling/threshold is changed to satisfy a limit.
`validation.reconstruction_points_v1` uses known scanned points as WORK total, with
observations as diagnostics. Unknown/zero detailed point work stays phase-only. Component
index is never overall progress. M6.5 ETA/history predicts only, never changes sampling or
policy. Cancelled/partial outputs cannot publish; restart uses existing M8 and completed
M9 stages. Checkpoint resume is not claimed.

## Explicit reconstruction selection

`ReconstructionSelection` v1 is a small immutable decision artifact referencing exact
ReconstructionSet, ValidationReport, metrics and canonical detailed geometry via manifest
lineage. It stores canonical selected component IDs and their camera/pose and detailed
geometry content digests. Duplicate/unknown/empty IDs are refused. Manual selection may
retain one or several components. Several components remain separate coordinate frames;
M10 emits separate datasets, with no implicit alignment, union or merge.

Manual choices record user intent and a reason; they are never called recommendations.
The one automatic policy is `selection.dominance_v1`. Coverage dimensions are always
registered-view count, total input coverage and coverage of **every** source group.
Per-component validation severity is also compared by default (PASS better than WARN).
Explicit required geometry comparisons can name metric/direction and whether sampled
evidence is acceptable. Unknown required comparison evidence never becomes perfect quality.
Point count and reprojection are not universal quality scores; neither ranks automatically.
Optional geometry comparisons are restricted to reprojection mean/RMS/p95/p99 (lower)
and triangulation median (higher). Point/observation counts are never quality-ranking inputs.

1. Remove components blocked by applicable FAIL issues.
2. No eligible component: return blocked, without a selection artifact.
3. One eligible component: select it and record `only_eligible_component`.
4. Several eligible components: require one component no worse in every required dimension
   and strictly better in at least one against **each** alternative.
5. Tradeoffs, equal evidence or missing required comparison evidence: return AMBIGUOUS,
   show structured candidates/reasons and require manual selection. No artifact is published.

The total-dominance test uses coordinate-wise optima in O(components * dimensions),
not an unbounded pairwise search. There is no weighted score, first/UUID tie-break,
implicit largest-component default or mapper feedback loop.

For a legal disjoint mixed fixture with 800 selected drone / 300 phone views, A has
500 drone + 20 phone (520 registered), B has 250 drone + 250 phone (500). A is larger
but covers only 6.7% of phone views; B covers 83.3%. A has better drone coverage while
B has better phone coverage. Neither dominates, so selection is ambiguous. The same
selected view cannot simultaneously belong to two M8 components.

## Failure scopes and exact overrides

Project-wide FAIL and source-group FAIL with no component ID apply to every choice.
Deselecting a component cannot waive them. Component and component/source-group FAIL
apply only when that component is selected. An independent unselected failure does not
block a clean component. Warnings require no override by default and remain referenced
in selection and visible through report/CLI; they are not silently suppressed.

An override requires exact reconstruction artifact ID and semantic identity, full detailed
geometry digest, report semantic digest, canonical selected component content, all exact
applicable failure issue IDs and a non-whitespace reason. Unknown IDs, warning IDs,
unselected issues, missing failures and duplicate IDs are refused. Automatic selection
does not override gates: explicitly choose components manually first. There is no
`--ignore-validation`. Changed geometry, selected components, report/measurement/policy
evidence or reconstruction publication makes the old override stale and requires new
explicit evidence. Report wording alone does not change stable issue IDs.

`require_current` rechecks selected numerical content and report binding for future
consumers. Component UUID identifies membership, not geometry. The same UUID with
changed cameras/poses or XYZ/observations cannot keep an old selection valid. Historical
selections remain inspectable against their immutable historical inputs; no mutable
"latest" reconstruction or grouping is substituted.

## Selection recipe and downstream semantics

The selection recipe includes report identity, mode, policy/settings, exact selected
component content, reasons and explicit override evidence. Its separate numerical
semantic digest includes ReconstructionSet semantics plus canonical separate selected
component IDs, component numerical digests and detailed validation geometry digests.
It excludes artifact UUID, policy, report gate, reasons/wording and runtime. Therefore
a different manual reason or policy can produce a new decision recipe with the same
downstream numerical semantics. A different selected component or its detailed sparse
content changes those semantics. M10 is implemented separately under [its own contract](M10.md).

| Change | Reused | Recomputed |
| --- | --- | --- |
| Validation thresholds | M8, canonical geometry, measurements | Report and selection/gates |
| Numerical sampling/method settings | M8 and canonical geometry | Measurements, report, selection |
| Manual selected components | M8 and M9a | Selection only |
| Selection policy/reason, same selected content | M8 and M9a | Decision recipe; same possible downstream semantic digest |
| Same component ID, changed cameras or detailed sparse content | Unaffected upstream stages | Geometry/metrics/report; old selection/override stale |
| Future M10 settings | M8 and M9 | Future dataset consumers only |

All four M9 stages publish/cache/recover through the existing execution repository.
`reconstruction.select` freezes exact evidence and the explicit decision; recovery
re-evaluates selection and overrides before adopting a fully verified orphan. Ambiguous
or blocked recommendations create no fake run/output. Selection cancellation publishes
no indexed result. Cache corruption is refused and a new immutable attempt can publish.

```powershell
splatforge reconstruction select "C:\Scenes\Example" --validation-run <uuid> --mode recommended
splatforge reconstruction select "C:\Scenes\Example" --validation-run <uuid> --component <a> --component <b>
splatforge reconstruction select "C:\Scenes\Example" --validation-run <uuid> --component <a> --override-issue <exact-failure-id> --override-reason "Reviewed this specific evidence."
splatforge reconstruction selection-show "C:\Scenes\Example" <selection-run-id> --json
```

Selection `--policy` accepts typed DominanceSelectionPolicy JSON. `--reason` records
manual intent. Ambiguous/blocked commands return exit code 2 with structured comparison;
invalid input/override returns 1. Successful inspection shows selected coverage, source
groups, reasons, warning IDs and exact overridden failures/reason.

## Integrity reuse without numerical rescanning

M9 uses a separate operation-scoped downstream read context. It freshly verifies the
indexed successful M8 producer, exact validated manifest and SHA-256/size of **every**
native payload, then reuses that publication's structural validation evidence. Metadata,
required files, path containment/independence and exact lineage are still checked. This is
explicitly reused structural evidence over freshly verified identical bytes, not a claim
of a fresh point/track scan. It needs no new state/cache system. A threshold-only run
neither deserializes sparse observations nor opens a validation geometry source. Ordinary
M8 publication/cache and M8 orphan recovery still run the original full native structural
validation unchanged.
