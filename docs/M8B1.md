# M8b1 Incremental Mapper and optional Caspar BA

M8b1 adds explicit `mapping.colmap_incremental` beside M8a's unchanged
`mapping.colmap_global`. Both publish **ReconstructionSet v1** and use the same
`ReconstructionReader`. There is no `mapping.colmap_caspar`: Caspar is an
Incremental bundle-adjustment backend. No mapper recommendation, ranking,
selection, alternate-mapper retry, Hierarchical, Global GPU, M9 or M10 is added.
The M7c production VPR benchmark remains pending independently.

## Single-model boundary

Incremental v1 fixes `Mapper.multiple_models=false`. Native Incremental multi-model
mode can emit overlapping registered-image hypotheses, whereas ReconstructionSet
components have disjoint UUID membership. These are different semantics. M8b1
does not drop overlap, assign views to an arbitrary model, merge hypotheses, select
the largest model or relax the set invariant. Unexpected multiple native models,
including disjoint ones, fail before publication. Zero models fail; exactly one
valid model meeting the explicit minimum becomes one component. All remaining
input views are explicit `unregistered_view_ids`.

Global continues to preserve all valid disjoint components, with its optional
explicit view-graph calibration. Incremental uses verified M7 camera state directly;
it never invokes that calibrator. Future native-overlap support requires a separate
contract design. Hierarchical's future internal overlapping clusters must be merged
natively before publishing portable components.

No ReconstructionSet/Reader schema, membership UUID, component/set semantic digest,
camera convention, native ID isolation or `unknown_arbitrary` scale rule changes.
Identical numerical output has identical public semantics across Global, Incremental
Ceres and Incremental Caspar. Mapper, BA settings and device belong to producer
provenance/recipe, not the output semantic digest.

## Installed backend evidence and settings

The configured native executable was inspected with `mapper -h` and
`bundle_adjuster -h` before implementing flags. Positively supported version remains
**COLMAP 4.2.1**, commit `bd1fcf6`, executable SHA-256
`9418a14c93d4a5eec5eb33ebf48a917403b5faa7ab5d2232f23e50c206d9e427`.
Later releases are refused until separately validated; `>=4.2.1` alone is insufficient.
The existing isolated M7b.3 runtime was used without modification or provisioning.

`IncrementalMapperSettings` is frozen, version 1, with this intentional subset:

| Settings | Default / supported values |
| --- | --- |
| `method_id` | `mapping.colmap_incremental` |
| `multiple_models`, `extract_colors` | false, fixed |
| `min_num_matches`, `min_model_size` | 15, 3 |
| `num_threads`, `random_seed` | 1, 0 |
| `min_focal_length_ratio`, `max_focal_length_ratio`, `max_extra_param` | .1, 10, 1 |
| `ba_refine_focal_length`, `ba_refine_principal_point`, `ba_refine_extra_params` | true, false, true |
| `ba_refine_sensor_from_rig` | false, fixed; current transport has only independent reference sensors |
| `ba_local_backend`, `ba_global_backend` | CERES/CERES or CASPAR/CASPAR; mixed configurations refused |
| `ba_use_gpu` | false, fixed; this native flag controls Ceres CUDA, not Caspar |
| `ba_gpu_index` | -1 for CPU Ceres; concrete nonnegative index required for Caspar |
| `ba_local_max_num_iterations`, `ba_global_max_num_iterations` | -1, pinned native defaults; positive explicit limits allowed |
| `ba_global_frames_ratio`, `ba_global_points_ratio` | 1.1, 1.1 |
| `init_num_trials`, `init_min_num_inliers`, `init_max_error`, `init_min_tri_angle` | 200, 100, 4, 16 degrees |
| `structure_less_registration_fallback` | true; explicit native 2D-2D registration within the same mapper/backend |

The native Ceres -1 iteration defaults resolve to 25 local / 50 global; Caspar's
native default is 200. Other unexposed controls are bound by exact executable and
runtime bytes. Native setting names are passed explicitly, including both backend
flags, both random-seed options, `Mapper.extract_colors=0` and `Mapper.multiple_models=0`.
There are no raw backend flags. CPU Ceres is the baseline; GPU Ceres is unsupported.
Resource limits refuse work rather than reducing BA iterations or changing algorithms.

## Caspar gates and restrictions

Capability facts remain independent: command presence, exact supported version,
typed Mapper options, implemented Ceres route, compiled Caspar, selected CUDA
device/runtime health, input compatibility, and real Incremental integration evidence.
Doctor reports separate `colmap.ba.caspar.compiled`, `.options`, `.runtime` and
`.integration` entries, plus Incremental command/version/integration entries.
Opening a project or running Doctor does not launch a reconstruction.

In exact 4.2.1, `BundleAdjustmentCaspar.*` help options are compiled only under
`CASPAR_ENABLED`. This is narrow build evidence; `Mapper.ba_gpu_index`, NVIDIA
inventory, CUDA DLLs and learned GPU inference are insufficient. A requested Caspar
plan additionally runs a bounded disposable native PINHOLE BA probe with real points,
explicit CASPAR selection and the concrete GPU index. CUDA device identity is read in
an owned disposable worker; the application does not initialize CUDA. GPU masking/order
environment overrides are refused because this v1 route cannot certify their ordinal
mapping. Device UUID/name/driver API/loaded-driver binary digest/compute capability and runtime enter frozen
backend identity. The device is checked again before the mapper attempt; substitution
or a failed device fails the attempt.

| Input / setting | Caspar 4.2.1 policy |
| --- | --- |
| PINHOLE | accepted |
| SIMPLE_RADIAL | accepted |
| SIMPLE_PINHOLE | rejected; the tiny Global/Ceres fixture is not a Caspar camera fixture |
| RADIAL / OPENCV / FULL_OPENCV | rejected, naming unsupported models before numerical attempts |
| Pose priors | rejected by existing classical mapping transport; no new pose-prior route |
| Non-reference rig sensor refinement | unsupported; route freezes refinement false and retains independent reference-sensor transport |
| Focal / extra refinement | must agree, both true or both false |

Camera compatibility is derived redundantly from the already validated frozen M7
database. It adds no convenience metadata to MappingInput or old Global recipes.
The adapter refuses unsupported cameras before native Caspar could skip observations.
Requested local/global CASPAR never changes to CERES. Positive Caspar solver logs
are required in addition to successful process exit and valid native output; reported
unsupported/skipped observations or BA/CPU fallback fail. No graceful solver-interrupt
claim is made: contained process-tree termination is the cancellation boundary.

Local evidence: **Caspar route implemented; compiled/available locally: no;
real-backend validated locally: false.** Installed help lacks the CASPAR_ENABLED-only
options. A separate disposable CUDA-runtime ordinal probe resolves device 0 to RTX 5080,
with UUID and driver binary digest retained in the private local report,
compute capability 12.0, driver API 13030
(NVIDIA inventory driver 610.62). No Caspar device was selected and no Caspar-compatible
execution is certified. No COLMAP build,
Caspar/CUDA installation, download, system PATH change or M7b.3 runtime mutation occurs.

## Isolation, identity and recovery

The same M8a path validates VerifiedGeometrySet and MappingInput, creates a fresh
independent attempt DB, strips descriptors/raw matches and undeclared geometry, seals
and rechecks it, then runs only against that private DB. Every attempt begins from M7;
it never reuses a Global-calibrated database. `mapping.db` preserves sealed input
evidence separately from the mapper's writable private copy. Source images are not
opened for sparse colors; the native image path is an owned empty directory.

Incremental's native per-model `project.ini` is moved, byte-preserving, within the owned
attempt to the existing `sparse/project.ini` provenance location. Reader and portable
model contents remain unchanged. Payload validation, cache and recovery enforce the
single-component receipt as well as native integrity and numerical semantics.

RunSnapshot schema 1 adds distinct `mapping.incremental.run` / `IncrementalMappingRoute`.
Old `mapping.run` / MappingRoute Global snapshots and M8a receipts remain readable;
their recipe identity is unchanged. Classical receipt settings accept the new typed
Incremental variant. No project/state migration occurs. Orphan adoption compares exact
frozen route, recipe, literal inputs and lineage; Global and Incremental artifacts cannot
be adopted into each other's runs even with identical portable semantics.

| Change | Reuse | Recompute |
| --- | --- | --- |
| Global / Incremental | all M7 artifacts | mapping |
| Ceres / Caspar; mapper settings or seed | all M7 artifacts | mapping |
| Caspar concrete GPU index/UUID/driver identity | all M7 artifacts | mapping and separate performance signature |
| Inactive resource limits; performance history | same numerical M7/M8 cache | no numerical work |
| Future M9 policy | M8 | future diagnostics/selection only |

Failures retain specific command/version/options/build/camera/device/refinement/input,
process/timeout/cancellation/teardown, zero/multiple/below-minimum/malformed/universe and
resource explanations. No failure launches a second mapper or BA backend. Cancellation
publishes nothing and preserves M7 plus previous M8 bytes. Unresolved teardown blocks
restart/publication. Resume is stage restart, not solver checkpoint resume.

## Progress and CLI

`mapping.incremental_phases_v1` uses M6.5 phase mode and historical whole-job duration.
Observable phases are `preparing_database`, `validating_mapping_input`,
`incremental_mapping` and `validating_output`. No native initialization/local/global BA
subphase is guessed. Post-validation diagnostics report registered/unregistered counts
and point counts. Registration counts do not authorize a fraction or linear ETA.
Cold ETA is unavailable; compatible history supplies a broad planning range. Global
CPU, Incremental Ceres CPU and Incremental Caspar/device signatures are distinct.
Failed/cancelled/cache-hit attempts do not teach history, and history never chooses a route.

```powershell
splatforge mapping run "C:\Scenes\Example" --verification-run <uuid> --method global --calibration preserve-priors
splatforge mapping run "C:\Scenes\Example" --verification-run <uuid> --method incremental --ba-backend ceres
splatforge mapping run "C:\Scenes\Example" --verification-run <uuid> --method incremental --ba-backend caspar --gpu-index 0
```

Without `--gpu-index`, the explicit Caspar CLI choice resolves to device 0 before
freezing the route. Typed `--settings` requires an already concrete Caspar index and
cannot be combined with individual numerical flags. Separate local/global fields are
Advanced typed settings, with only the two tested product combinations accepted.
