# M10 flat-camera dataset preparation

M10 technical dataset-preparation implementation is complete, consuming a published M9 selection.
Production automatic multi-video E2E acceptance remains pending **M7c production VPR
selection**. An explicit bounded Exhaustive/Sequential/reference selection is a legal
dataset input, not proof of production retrieval. The local mixed phone/drone pilot
does not select a universal mapper, pairing method or product default. [M11](M11.md)
consumes the existing component contract without redesigning dataset preparation.

## Immutable inputs and separate outputs

```text
ReconstructionSelection v1
  -> exact ReconstructionSet + M9 geometry/report/override
  -> exact historical SelectedViewSet / CandidateViewSet
  -> registered pixels of each selected component
  -> independent PreparedDatasetComponent v1 publications
  -> PreparedDatasetSet v1 receipt
  -> M11 external handoff or separate managed component training
```

`dataset plan/prepare --selection-run` accepts only an explicit successful published
selection run. Mapping run IDs, folder numbers and implicit largest/first choices are
refused. Planning, execution, indexed reads and recovery reuse M9's existing input
checks and `require_current`, including exact reconstruction identity, selected component
camera/pose digest, detailed geometry digest, report evidence and exact FAIL override.
Warnings and the current valid override remain in provenance. An unpublished ambiguous
recommendation cannot become a dataset. Several chosen components remain several
independent coordinate systems and datasets; there is no union, alignment or point merge.

Historical lineage follows ReconstructionSet -> VerifiedGeometrySet -> MatchSet ->
LocalFeatureSet -> CandidateViewSet/SelectedViewSet, using exact indexed manifests.
M10 never opens original source MP4/JPEG files. Moved/missing originals do not block
preparation when immutable historical pixels are intact. Missing/corrupt historical
pixels fail; there is no source fallback. Explicit upstream rebuild is required.
The attempt copies only `component.registered_view_ids`, verifies their hashes/decodes,
and gives COLMAP independent copies. No writable hardlinks or original recompression.

## Contracts and identity

Method: `dataset.colmap_undistorted_v1`, role `dataset_preparation`. Artifact types:
`dataset.prepared_component` and `dataset.prepared_set`, contract 1. No project/state
schema migration or M7/M8/M9 schema change is needed.

PreparedDatasetComponent records source component ID, M8 component semantic digest,
M9 detailed validation-geometry content digest, exact selected view/image mapping,
M10 canonical consumed sparse digest (also binding preserved RGB/stored error),
image/camera/point counts, output image SHA-256/size/dimensions, canonical cameras and
camera_from_world poses, sparse numerical digest, preserved world-point/track digest,
format, convention, unknown scale, frozen settings, backend numerical identity,
layout, omitted unused-feature count and provenance. `dataset.json` records its recipe/numerical digest and
derived membership/count/model summaries, checked by the reader. Large point arrays
remain in binary sparse files, not JSON. Source artifact/report/selection references,
warnings, override and pairing method/readiness are explanatory provenance.

The component recipe hashes versioned method/settings, selected component M8/M9
numerical content, exact consumed view IDs/pixel hashes/dimensions and pinned native
executable/runtime identity. It excludes artifact UUIDs, decision reason/report policy,
mapper/pairing labels, paths, resource budgets, warning text, time, progress and ETA.
It does not hash the entire selection/set, so an unaffected component can be reused.
M10's source sparse digest additionally binds point colors and stored native errors,
which M9 deliberately does not consume; neither native IDs nor unused feature rows
enter that canonical projection.

Component semantics hash actual prepared membership, image bytes, canonical camera/
pose content, XYZ/color/stored error/tracked-observation content and resolution settings.
The diagnostic count of omitted unassociated features is excluded from numerical identity.
Native image/camera/point IDs, point order, model folder number and quaternion sign
are not semantic identity. A disk-backed canonical stream orders numerical point and
track digests without loading the point cloud into application JSON.
The DatasetSet numerical digest covers the canonical ordered independent component IDs
and numerical dataset digests. Its small recipe additionally freezes the exact current
decision and component references. A new decision reason can reuse the component but
publishes a fresh receipt carrying current gate/provenance; cached component metadata
retains its original producing lineage.

## COLMAP and numerical preparation

Positively supported runtime: **COLMAP 4.2.1 / bd1fcf6**. Exact executable and runtime
DLL identity are pinned and checked before/after launch. Later versions need positive
validation. Doctor separately reports command presence, supported version, required
undistorter options, runtime identity and integration status; mapper availability does
not imply undistorter availability. Doctor help evidence leaves real integration unknown.

The installed `image_undistorter -h` was inspected. Required explicit options are:

| Option | Frozen value |
| --- | --- |
| image_path / input_path / output_path | independent attempt-owned paths |
| output_type / copy_policy | COLMAP / COPY |
| max_image_size | -1 for None; explicit positive maximum side otherwise |
| blank_pixels | 1.0, retain available field of view within scale bounds; blank borders allowed |
| min_scale / max_scale | 0.2 / 2.0 |
| roi_min_x / roi_min_y / roi_max_x / roi_max_y | 0 / 0 / 1 / 1 |
| jpeg_quality | -1, native default bound to exact runtime |
| num_threads / default_random_seed / log_target | 2 / 0 / stderr |

Settings v1 deliberately exposes only `max_image_size`; other output-affecting values
above are fixed schema constants. Remaining native defaults bind exact runtime bytes.
`observation_policy=registered_sparse_tracks_v1` is also fixed: retain every 3D point
and reciprocal tracked observation, omit unassociated feature rows, and remap indices
in both directions using a bounded disk index. Unused features are not sparse tracks
or trainer data. COLMAP can turn their out-of-domain coordinates into NaN during inverse
distortion; no NaN is allowed in published output. This policy changes no registered
image, camera, pose, point or supported track. Metadata records the omitted count;
an unprojectable tracked observation still fails validation.
These are conservative initial product choices, not universally optimal calibration
or image-quality settings. No second encoding pass or ImageMagick dependency is added.

Input models: SIMPLE_PINHOLE, PINHOLE, SIMPLE_RADIAL, RADIAL, OPENCV, FULL_OPENCV.
Only independently validated SIMPLE_PINHOLE/PINHOLE outputs publish. Fisheye,
equirectangular and panorama models fail with the M10 flat-camera boundary. There is
no implicit crop into a pinhole camera. Future 360 preprocessing remains M14.

`max_image_size=None` preserves native undistorted resolution, without an extra resize
limit. Distortion removal itself can change dimensions/intrinsics and introduce blank
borders. A positive value constrains width/height through the same native camera/pixel/
observation transform. There is one canonical resolution, no images_2/4/8 pyramid.
Changing it rekeys M10 only. Resources never silently change this value or drop views.

The adapter builds a component-specific legacy three-file native input, preserving
M8 cameras, camera_from_world poses and every supported XYZ/tracked observation while naming
images `<public-view-uuid>.png` or `.jpg`. Only independent reference-camera frames
already supported by M8 are accepted. M8 native payloads remain unchanged; only the
attempt-owned transport observation indices are remapped.

Pinned upstream references: [camera/observation transformation](https://github.com/colmap/colmap/blob/bd1fcf6/src/colmap/image/undistortion.cc)
and [undistorter CLI](https://github.com/colmap/colmap/blob/bd1fcf6/src/colmap/exe/image.cc).

## Trainer layout and independent validation

Each referenced component artifact is already usable as a conventional COLMAP dataset:

```text
artifacts/dataset_component/<artifact-uuid>/
  images/<view-uuid>.png|jpg
  sparse/0/cameras.bin
  sparse/0/images.bin
  sparse/0/points3D.bin
  dataset.json
  manifest.json
artifacts/dataset_set/<artifact-uuid>/
  dataset_set.json                    # references components; no copied image payload
  manifest.json
```

`dataset show` prints each ready component directory. No second export/copy command
is required. External destination copying is not implemented in M10. Immutable cached
directories are inputs; a future writable trainer must own its output/workspace and
must not edit published datasets. Even an accidentally edited dataset cannot mutate
the independently copied upstream CandidateViewSet.

The standalone adapter reader opens files on disk. It checks the exact public layout,
safe relative names and plain independent files, no extra/missing images, full image
decode/hashes, dimensions equal to camera dimensions, every image's supported camera,
finite valid poses, exact membership and bidirectional point/track references. Camera
and pose summaries and sparse numerical identities must agree with dataset.json.
Publication/recovery additionally compare the selected M8 source: world XYZ and
public track membership must be identical independently of native point IDs, rotations
and translations agree within absolute **1e-8**, and each transformed observation ray
projects through the original camera within **1e-4 source pixels**. Original distorted
XY is not compared directly to undistorted XY. Malformed or nonfinite output fails
even after exit zero. SfM scale stays `unknown_arbitrary`, never meters.

## Planning, resources and lifecycle

```powershell
splatforge dataset plan "C:\Scenes\Example" --selection-run <uuid> --colmap "C:\Runtime\bin\colmap.exe" --json
splatforge dataset prepare "C:\Scenes\Example" --selection-run <uuid> --max-image-size 2400 --json
splatforge dataset show "C:\Scenes\Example" <dataset-run-id> --json
splatforge run active "C:\Scenes\Example" --json
splatforge run show "C:\Scenes\Example" <component-run-id>
splatforge run progress "C:\Scenes\Example" <component-run-id> --json
splatforge run cancel "C:\Scenes\Example" <component-run-id>
splatforge run recover "C:\Scenes\Example" <interrupted-run-id>
```

The plan reports selected components/registered counts, exact historical pixel artifact,
input camera models, distortion need, frozen max side, native evidence, validation/
override/warnings, per-component cache reasons and free/required disk. It creates no
dataset publication. `SPLATFORGE_COLMAP` follows normal existing executable resolution.
Status/cancel/recover remain generic. `run active` discovers the current run ID and
phase without the writer lock, so another CLI can cancel a synchronous preparation.
Restart is a new `dataset prepare` that reuses completed components; generic
`run retry` remains fake-only. No checkpoint resume is claimed.

Disk estimates distinguish measured compressed input bytes, expected compressed output,
conservative output and decoded working memory. Dimensions may expand up to native
max_scale per axis before the max-side cap. Expected output uses scaled encoded input
or 0.3 bytes/pixel; conservative output uses twice scaled input or 2 JPEG/3.2 PNG bytes
per pixel plus 64 KiB/image. Sparse/index allowance is 4x input sparse bytes, metadata
4 KiB/image + 8 MiB. Compressed sizes are estimates, not exact upper bounds. Actual
workspace growth, free disk and time remain enforced. No 100+ GiB decoded-memory
formula is misrepresented as disk use.

Default limits: 32 GiB per component workspace, 256 MiB free-disk safety margin,
7200 seconds per component, 1000 components. `--max-workspace-gib`, `--minimum-free-gib`
and `--timeout` change refusal limits only. The set plan includes accumulation of
previous completed outputs plus the next component's peak. After full validation,
attempt-owned input/native scaffolding is released; publication is a same-volume
rename without another large image copy. No dense-stereo scaffolding is published.
The existing reader's image decode limits still apply (64 million pixels/image).

`dataset.undistortion_phases_v1` uses M6.5 phase mode: materializing_input,
validating_input, undistorting, validating_output, publishing. It records images and
input megapixels as workload. No percentage is inferred from native text or elapsed
time. Whole-job historical ETA partitions settings, backend/runtime and hardware;
cold ETA is unavailable. Failed/cancelled/cache attempts do not teach history.

Contained execution uses existing Windows Job Objects, argv arrays, explicit cwd,
scoped runtime environment, bounded streams, timeout and process evidence. Cancellation
requires durable owner acceptance and confirmed tree teardown; unresolved teardown
blocks retry/publication. A later component's cancellation retains earlier published
components for reuse, but publishes no final DatasetSet. Complete orphan adoption
rechecks exact selection/settings/backend/lineage, all image hashes, membership,
sparse structure and source preservation. Partial output is not adopted.

## Manual cleanup and cache eviction

```powershell
splatforge project cleanup "C:\Scenes\Example" --dry-run --json
splatforge project cleanup "C:\Scenes\Example" --artifact <uuid> --dry-run --json
splatforge project cleanup "C:\Scenes\Example" --artifact <uuid> --apply --preview <preview-digest>
splatforge project pin "C:\Scenes\Example" <artifact-uuid>
splatforge project pin "C:\Scenes\Example" <artifact-uuid> --unpin
```

Cleanup takes artifact IDs, never arbitrary paths. Apply requires the exact digest of
a fresh matching preview under the project writer lease. Preview mutates no project
files/state. The latest successful output binding per artifact kind (including a cache
hit on an older publication) and newest successful publication are implicitly protected,
as are explicit pins, active/unresolved attempt inputs and active/interrupted outputs;
their entire exact lineage closure is protected. This conservative current policy may
retain more than a future storage manager. Removing an explicit pin cannot remove an
implicit dependency protection. Historical references alone are not permanent pins.

Only completed unprotected generated payload files may be removed. JSON metadata,
manifests, state, source inventories, originals, active attempts, external exports and
checkpoints survive. All target paths/hashes/ownership are checked before deletion;
symlinks/junctions/hardlinks/traversal fail closed. No recursive arbitrary-path deletion.
`state.sqlite.metadata[storage.retention_v1]` durably records pins and `evicting` intent
before unlink, then `evicted`. Interrupted deletion remains diagnosable and requires a
fresh preview to finish. Cache lookup distinguishes intentional eviction from corruption
and recomputes; it never claims a missing payload is a hit. Eviction does not rewrite
the immutable manifest. Automatic retention remains M13d.
